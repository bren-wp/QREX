# QREX — Android 1.0.1 full source/code/dead-code audit

**Audit date:** 18 October 2026 · **Scope:** current Kotlin/Jetpack Compose Android code, Gradle/manifest, resource generator, 23 locale sets, Android tests, GitHub Actions, signing/release scripts and published documentation.  
**Base:** GitHub `v1.0.0` (`c3ae2d69daebe46d273cbe01b75e0edc0c841a01`) · **Candidate:** Android `1.0.1` / `versionCode 101`.

## Verified repository architecture

- **Six application Kotlin modules:** `MainActivity.kt`, `QREXCore.kt`, `QREXScanner.kt`, `QREXDocuments.kt`, `QREXSecretCipher.kt`, and generated `QREXStrings.kt`.
- Single native Android module with `minSdk 26`, `compileSdk 36`, `targetSdk 36`, Kotlin/Compose, CameraX, bundled on-device ML Kit barcode scanner and ZXing.
- No active Swift/iOS application, Flutter runtime or redundant old app build pipelines.
- Legitimate system entry points (Android `MainActivity`, lifecycle callback, CameraX `ImageAnalysis.Analyzer.analyze`, Compose `@Composable` methods) are not dead just because a static search shows one occurrence.
- Original Flutter `SharedPreferences` upgrade reader and the Wi-Fi Keystore AES-GCM implementation **must remain** so migration and existing protected data do not disappear.

## Duplication / resource analysis

- PDF/ZIP export now reuses `writePdf(records, stream)` instead of separately allocating full PDF byte arrays and duplicating IO structures.
- Shared version/signing metadata is checked through Gradle and `check_native_release.py`; the protected Play publisher and GitHub-only publisher explicitly have **different signing semantics**.
- `MainActivity` contains public-facing Compose screens in one source file and uses composable helpers; a later architecture cleanup could split screens without changing the product design, but massive unrelated refactoring immediately before an Android release would increase regression risk.
- Full deep proof that all dynamic/framework-referenced code is used is not possible with text search alone. R8 `isMinifyEnabled=true` and resource shrinking remain enabled, and Android lint, JUnit, instrumentation, emulator QA and real-device profiling are the layered safeguards.
- Historical audit/release Markdown and approved SVG preview assets are retained for provenance. These are **not** unused runtime code.
- Removed the obsolete release-retirement shell script, obsolete recovery workflow and isolated fake API tests; no automated path may delete previous GitHub Release assets on 1.0.1 publishing.

## Security & privacy

- The app source only requests `CAMERA`, and permission prompting is user-initiated. Photo scanning uses the system photo picker without broad gallery permission.
- Scans/QR generation are on-device; no developer backend, advertising/analytics SDK or intentional internet permission. **Do not declare that no information is collected until actual merged manifest and dependency/runtime checks agree**, including bundled SDK behavior.
- Saved Wi-Fi secrets remain AES-GCM encrypted in Android Keystore. The app does not auto-save Wi-Fi payloads. Clipboard contents are tagged sensitive, and Wi-Fi share requires confirmation.
- User-selected exported PDF/ZIP destinations can contain unencrypted sensitive contents; accurate export warnings were fixed.
- Scanned HTTP(S) links are only opened after a user action; URL host/control/whitespace/user-info checks remain in place.
- The Android history loader rejects corrupted/undecryptable protected history to avoid silently overwriting it. Future UX improvements could offer explicit recovery/export diagnostics without exposing secrets.

## Google Play compliance and release limitations

- New/updated phone apps submitted to Google Play on or after **31 August 2026** must target API 36 or above; QREX has target 36: https://support.google.com/googleplay/android-developer/answer/11926878
- Google Play Data safety and publicly reachable privacy policy must be completed, including real SDK practices: https://support.google.com/googleplay/android-developer/answer/10787469
- 16-KiB page support for native libraries: https://developer.android.com/guide/practices/page-sizes
- Proper Play App Signing/update identity: https://developer.android.com/studio/publish/app-signing
- Applicable new individual-account testing requirements may include 12 opted-in testers for 14 continuous days: https://support.google.com/googleplay/android-developer/answer/14151465
- **v1.0.0 GitHub assets are immutable historical builds with an ephemeral certificate. They cannot be retroactively turned into Play-signed artifacts.**
- **The GitHub v1.0.1 APK and AAB use a different disposable certificate**, so GitHub 1.0.0 installs will not upgrade in place. The protected 1.0.1 Play upload AAB uses the developer's actual verified upload identity when secrets are provisioned.
- Without Play Console and a real upload key, no assistant can honestly claim the AAB is uploaded/approved. The versionCode may need advancing further if 101 was already consumed in that Play app.
